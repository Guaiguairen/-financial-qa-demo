## 二、两处关键工程决策

**1. 解析档位选择（basic vs flash 实测对比）**
- 表格输出：同一页的表格 HTML 在两个档位下**逐字节一致**（含带 rowspan/colspan 多级表头的权益变动表）——对带文本层的电子版 PDF，两档共用原生版式解析路径；
- 差异在标题标注：basic 检出约 4 个标题/页（含"合并资产负债表"等无编号标题），flash 稀疏，但其缺位可由中文标题模式（第X节 / 一、 / （一））启发式补齐；
- 运行成本：本机 6GB 显存环境下 basic 档出现严重性能波动（版面推理 0.08s/页 → 最长 120s/页），flash 稳定约 4 页/秒、内存占用低。
- **结论：flash 档全量解析**，并把该对比作为评测的一部分接受了检验（未发现表格质量损失）。

**2. 混合检索的融合与加权**：向量与 BM25 各取 Top-50，RRF 融合；针对真实失败案例迭代增加了三类加权（公司名提及、期间消歧、叙述型数据），并据此修复了评测中最高频的"母公司口径抢占 Top1"问题。

## 三、评测分析：哪类题答得好，哪类翻车

**整体成绩**：单公司事实题 4/8 正确；跨公司全景题 0/2；合计 4/10。

**答得好的**——指向管理层讨论中"叙述型数字"的题目（q01/q05/q06/q07）。当正确证据（如"实现营业收入 649,719.62 万元，同比增长 453.21%"）进入 Top 证据时，1.7B 小模型也能稳定做到精确提取、口径标注（如"合并口径"）和章节页码引用。业务分部（表格类）问题同样表现良好。

**翻车的四类，原因各有不同**：

1. **数字与单位误读（q02、q04）**：模型把"内部开发支出 376,765,402.88""母公司净利润 -190,221,418.83"等**近似数字**误当目标值，且单位（元/万元）处理错乱。这是生成模型能力瓶颈——1.7B 对密集数字表格的"数字-标签"绑定不可靠。
2. **口径混淆（q04）**：把母公司报表数据当作合并口径归母数据。检索无法识别表内口径标签（"母公司利润表"标题与数据块分离），模型也无此先验。
3. **期间错配（q03、q08）**：多期报告共存时（全年 vs Q4、2025 vs 2026 半年报），"当期主叙述"与"同比对照数据"的消歧失败——q03 取了 Q4 数据、q08 的当年叙述块未被召回。
4. **全景题失效（q09、q10）**：跨公司对比需要"公司名-数字"的严格绑定与多实体汇总。单轮证据容量有限（见下），压缩后的证据让 1.7B 发生实体错配（把海光营收记到寒武纪名下）；q10 还把"研发人员占比 89.4%"误读为"研发投入占比"。

**一个贯穿性的结构性发现**：6GB 显存下，生成本地模型的证据预算存在硬约束——提示词超过约 2.4k token 即触发显存换页（生成速度 13 tok/s → 0.5 tok/s）。两轮调参（2400 字 vs 3000 字）证明：**预算收紧会产生"截断型失败"（关键数字被裁），放宽则逼近显存悬崖**。这是小显存设备上"完整性-稳定性"的真实权衡，也是本系统下一步最值得工程的环节。

## 四、已知局限与改进方向

1. **表格结构化三元组**：把关键表格行抽取为（项目，数值，单位）三元组再入证据，规避模型直读原始 HTML 表格——直接针对 q02/q04 类失败；
2. **两段式全景问答**：先按公司分组检索与抽取、再 map-reduce 汇总，解决 q09/q10 的覆盖与绑定问题；
3. **口径与期间标签**：对"母公司/合并""季度/半年/全年"语句自动打标签并参与检索过滤；
4. **生成模型升级**：当前 1.7B 的能力边界已在多处显现；接入更大本地模型或 API 是性价比最高的单项改进；
5. **PDF 源数据瑕疵**：个别表格在 PDF 本身存在字符错序（如某权益变动表数字呈"632,,.225584"），属源文件问题，两种解析档位均无法修复——评测中已回避此类数字作为考点。
